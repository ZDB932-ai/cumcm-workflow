# 验证与证据发布

本文件唯一规定 Evidence 生命周期、Micro Review 和最终审查的验收含义。

## 1. Evidence 状态

| status | 含义 | 使用边界 |
|---|---|---|
| candidate | 已有真实记录，尚未完成适用验证 | 可分析/写带标记草稿，不作确认结论 |
| verified | 针对所记版本、范围与方法完成检查 | 在明确适用范围内使用 |
| stale | 上游版本、验证依据或当前关联已失效，待复核 | 不能作当前已验证结论 |
| rejected | 有证据证明该记录的内容/结论不成立 | 保留错误依据，不采用该错误结论 |
| obsolete | 被新版本取代，但不表示原记录错误 | 有效性仍可核对时，仅作明确标注的历史/基线比较 |

正常发布 candidate -> verified；未检查仍为 candidate，不能因缺时间改成 rejected。
验证发现错误可转 rejected；已发布依据失效转 stale。
stale 经相同内容/原版本的重新核验可恢复 verified；内容修正则建新记录并关联旧记录。
旧记录被替代可标 obsolete，不抹去原验证记录。
一个失败的 EXP 可以 verified：只表示“该失败运行被核实”，不表示其模型成功。
程序运行成败记在 run_status；validation.outcome 表示对记录内容的核验结论。
例如 run_status=failed、validation.outcome=passed 可表示失败过程已核实；
validation.outcome=failed/not_checked 与 verified 冲突，不能混用两个字段消除冲突。
新写核验结论优先用 passed / failed / not_checked；旧自由文本按具体范围核对，
不因不符合新写法自动否定其证据。

## 2. 发布条件

candidate 创建者可以做自测，发布者为 Coordinator。独立检查可以由其他 Agent、
人或不同方法完成；“换了一个 Agent”本身不是独立证据。

验证记录须有：checked_by、checked_at、method、scope、input_versions、
checks_run、outcome、limitations；以实际命令/输出、推导步骤或来源核对支撑。
Coordinator 需核对交付物、依赖、单位、指标含义和输入版本，再更新 status。
支持正式结论的依赖应为适用的 verified 证据，或经核对仍有效且明确作历史对照的
obsolete 证据；candidate/stale/rejected 不能作为未经说明的已验证支撑。
作者自测但没有适用独立依据时，明确保留候选或缩小“已验证”的范围。
验证发布与用户批准方案相互独立：候选试验可按实际检查范围 verified，
但正式采用其主方案仍须满足 [user-intent.md](user-intent.md) 的关键决策确认。

| 类型 | 最低适用核对 |
|---|---|
| model | 假设/公式/变量范围与题意一致，具有可实施或可证明定义 |
| experiment | 实际执行或推导过程、输入版本、参数、退出/失败记录可核对 |
| result | 由真实过程导出，单位/指标正确，至少一种适用独立核对通过 |
| fact | 可定位原始来源、原文/字段/页码，结论不超出来源 |
| figure | 数据版本、生成过程、坐标/图例/单位与所支持结论一致 |
| claim | 依赖可用，比较口径和计算正确，文字强度与证据范围一致 |

type 专属字段见 [evidence 模板](../templates/evidence.md)。
claims 不限于数值结论；理论性质可由 verified model/fact 和证明支持。
根据来源强度说明不确定性，不能把“没发现错误”写成普遍正确性证明。

## 3. Micro Review

每个选定结果拟升级 VALIDATED 前做轻量核对：
模型与题意、数据与处理、代码/推导与输出、单位、数量级/可行性。
预算通常 5-15 分钟起，按风险扩展；时间长度不是验证充分性的标准。
发现单位或索引错误时保留候选/失效标记，修复后重新核对。
Minor 留在 TASK/Review；实质阻断建 ISSUE，不要求每次检查都新建 DEC。

实现审查从正式入口、实际配置和调用链到运行产物，不从孤立函数或旧说明推断行为。
题面/有效决定说明预期，调用链/存盘结果说明实际；两者冲突时分别定位。
按任务区分验证范围：输入与时间轴、实现与可行性、数值复现、统计评价、论断、
文件格式/视觉。优化求解的可行解、达到容差的最优性与全局最优证明不可混称；
时间限制退出需报告可行性、界限或 gap（若可用）。
单位和索引检查用独立关系或短例，不能仅调用同一个可能有错的计算函数自证。

## 4. 一致性与更正

论文数字 -> Claim/Result 的明确字段 -> 对应文件 -> 代码/推导和输入版本。
核对数据范围、参数、单位、百分比、舍入方式和图表版本。

若只是论文抄错数值，应按已验证输出更正论文，无需改正确程序。
若代码/数据本身错，则修复计算、重跑必要实验并更新受影响证据和论文。
篡改正确输出来迎合论文预期才属于伪造，不能把正常勘误误判为伪造。
影响传播见 [memory.md](memory.md)；可只重新审查受影响链路。
文本小修检查修改段落及受影响引用/导出；全局样式、分页或模型改变再扩大范围。
未改变的完整实验已有有效验证时不机械重跑；新输入、失败或未解疑点才扩大检查。

## 5. Final Review

优先独立读题目与稿件，再按论断索引抽查关键源证据；
不要默认读全部 Evidence，也不能禁止查看失败实验或反例。
检查是否答题、模型合理性、复现依据、数字一致、符号单位、局限、
引用真实性、AI 使用记录、匿名/格式及提交材料。
按必答清单逐项检查解释性问题，不因结果文件齐全就宣称全题完成。
适用规则要求人工核验时，最终交付验收必须有真实核验者、版本、范围和反馈记录；
Agent 审稿、程序检查与人工核验分别记录，缺项只阻塞相应的最终验收。

输出 [review 模板](../templates/review.md) 中的 Critical / Major / Minor / Optional。
Critical 或会使必要结果不可信/违反要求的 Major 阻断相关验收；
非阻断 Major 可说明修复计划或局限。不能通过改低严重性规避错误。
修复后记录复核，未检查的范围明确列出。Review 默认不自行改稿。
